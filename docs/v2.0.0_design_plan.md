# Achelife v2.0.0 design implementation plan

## Goal and source of truth

Redesign the whole app as one coherent interface while preserving its existing behavior and data. The version is **2.0.0** even though the current branch name mentions 1.4.0; the branch name does not define this plan or the release version.

The [UI and motion guide](ui-design-and-motion.md) defines color, material, typography, controls, accessibility, and motion. The [page layout and hierarchy guide](ui-layout-and-hierarchy.md) defines page rails, headings, navigation levels, spacing, and control sizes. Read both before **every** phase. The [global UI foundation](v0.1.0/phase-0.5-global-ui-foundation.md) describes existing primitives and behavior; when it differs from the newer guides, use the newer guides as the redesign target without breaking persisted values. The [user guide](user-guide.md) records current user workflows. Feature-specific docs linked below define behavior that the redesign must retain.

This is a design and presentation release. A phase may change storage only where the agreed appearance features require it. Do not expand Task, Money, Habit, Season, or other domain rules as part of a visual phase. Keep the application usable at the end of each phase.

## Working rules for every phase

1. Read this plan, both design guides, the phase's feature docs, and the relevant current code before editing. Map each screen to page rail, header, module navigation, local views, filters, content, and feedback states as required by [the layout adoption rule](ui-layout-and-hierarchy.md#adoption-rule-for-agents).
2. Implement one numbered phase at a time. Finish its review and report before starting the next. Fix a shared token or primitive at its source when a page exposes a shared problem. Avoid page-specific copies of the design system.
3. Preserve route behavior, keyboard and focus behavior, saved view state, data loading, mutations, and domain calculations. Preserve existing `normal` and `glass` appearance meanings, old accounts, archives, imports, exports, upgrades, and configuration. For any new persisted palette or style value, use safe defaults and explicit compatible archive handling; do not rewrite old migrations or versioned formats. Follow [the appearance compatibility notes](ui-design-and-motion.md#implementation-boundaries-and-known-follow-up) and [account portability](v1.0.0/phase-15-account-data-portability.md).
4. Keep high-level flow readable, name actions by intent, and split files before they exceed 500 lines. Use shared components for proven recurring roles. Make no unrelated product changes.
5. Use the nearest free development port in **8000–8009** for any UI review. Do not alter an installed Docker instance, including the one on 8081.
6. Give the user the phase's manual checklist. Record what was changed, which docs governed it, compatibility effects, known limitations, and a suggested commit message. The user performs visual and workflow testing. Add focused regression coverage only when a phase changes persisted appearance data or archive handling, as required by repository compatibility rules; avoid broad UI test runs for a visual-only phase.

### Common manual review for each visual phase

Apply the [UI review matrix](ui-design-and-motion.md#review-matrix-for-every-new-or-redesigned-screen) to changed screens: Light and Dark with each **available** surface style, desktop and narrow/mobile widths, long labels and large text, keyboard and visible focus, empty/loading/error/populated states, reduced motion, and the built-in background. Check a bright, dark, and busy uploaded image to assess the Settings warning. Check System mode when the device theme changes. Include the blur fallback and reduced transparency where supported. Measure text and control contrast against the rendered surface, including the worst built-in wallpaper patch. As Normal glass becomes available, include it in every later phase.

### Phase 0 — Baseline and screen inventory

**Implement:** Inventory every authenticated and first-run route, existing shared components, current tokens, appearance storage, and unfinished redesign work. Capture the current navigation, width, heading, and control inconsistencies already identified in [the layout audit](ui-layout-and-hierarchy.md#current-app-audit). Record the key existing workflows from the [user guide](user-guide.md). Decide the palette storage shape, derived-color rules, archive adapter, and rollout order before changing persistence; document those decisions against [theme palettes](ui-design-and-motion.md#theme-palettes). Establish a small review record for each phase with representative screenshots and known exceptions.

**Manual gate:** Open every route once at desktop and mobile size; identify any route that already fails before redesign. Confirm the inventory includes setup, onboarding, intermission, closeout, and restore, not just the main app.

### Phase 1 — Semantic tokens, typography, and material system

**Implement:** Build the shared semantic palette for Light and Dark, starting with cool porcelain Light and preserving the character of Dark glass. Keep League Spartan throughout the interface. Define the page, surface, raised, and inset depth roles; Normal solid, Frosted glass, and Normal glass material recipes; layered corners; glass edges; unfiltered wallpaper; blur fallback; and reduced-transparency treatment. Keep existing saved `normal` and `glass` values unchanged. Centralize tokens in the shared CSS/theme layer before moving pages. Follow [semantic roles](ui-design-and-motion.md#rules-in-priority-order), [theme palettes](ui-design-and-motion.md#theme-palettes), [surface and depth](ui-design-and-motion.md#surface-and-depth-system), and [text, icons, and data](ui-design-and-motion.md#text-icons-and-data).

**Manual gate:** Inspect a component showcase or representative shell, nested card, input, and overlay in both themes and all material recipes. Check readable text, visible edges, fallback without blur, and no unintended change to saved Normal/Frosted glass behavior.

### Phase 2 — Shared controls and page structure

**Implement:** Update shared Button, Surface, form, dialog, drawer, status, chart, and navigation primitives to use the new tokens and material depth. Add consistent page rail, page header, module navigation, and local-view patterns. Apply the 80rem standard rail, justified 92rem wide rail, heading scale, 4px spacing rhythm, and documented control heights. Route links use `aria-current`; in-page tabs follow the tab pattern; filters remain controls. Cover hover, focus, selected, disabled, loading, success, and error states. Follow [controls and states](ui-design-and-motion.md#controls-and-states), [motion](ui-design-and-motion.md#motion-language), and the full [layout guide](ui-layout-and-hierarchy.md).

**Manual gate:** Navigate by mouse, touch, and keyboard through the shared controls; open and close dialogs/drawers and confirm focus return. Check 320px reflow, 200% text scaling, target sizes, safe areas, reduced motion, and fixed controls that could obscure focus.

### Phase 3 — App shell, global navigation, and Today

**Implement:** Apply the page frame to the sidebar, mobile navigation, persistent progress panel, Dynamic Island, and Today. Give global location the strongest cue and align Today sections to the shared hierarchy. Keep Tasks, Habits, Diary, progress, timer, and SP interactions intact. Use [page composition](ui-design-and-motion.md#page-composition), [navigation hierarchy](ui-layout-and-hierarchy.md#navigation-and-tab-hierarchy), [Today behavior](user-guide.md#today), and the [global foundation](v0.1.0/phase-0.5-global-ui-foundation.md).

**Manual gate:** Switch modules on desktop and mobile; use Today Tasks/Habits, open progress, and run a Focus timer through navigation and reload. Confirm the bottom bar and floating controls leave content and focus visible.

### Phase 4 — Tasks and Focus

**Implement:** Redesign Tasks workspace, Files, Inbox/Projects, Calendar, Task details, Focus history, and Task Statistics with the shared page and control patterns. Preserve the established Folder → Project → Task structure, occurrence-specific changes, drag and accessible movement, Focus timing, and statistics definitions. Document any 92rem rail use for workspace/calendar. Follow [Tasks behavior](user-guide.md#tasks), [Tasks 2.0 roadmap](v1.3.0/README.md), [Task statistics](task-statistics.md), [task targets](task-targets-plan.md), and both design guides.

**Manual gate:** Create, edit, move, complete, undo, reschedule, and filter Tasks; inspect Calendar; start, pause, switch, and finish Focus; inspect statistics. Check long names, large collections, dialogs, charts, and keyboard alternatives to drag.

### Phase 5 — Seasons, Habits, Diary, Constitution, and progression

**Implement:** Apply the shared hierarchy and material system to Season introduction, command center, objectives, statistics, Rank, closeout/intermission, Habits and Habit Statistics, Diary/People, and Constitution. Preserve historical attribution, calendars, streaks, autosave, violations, and lifecycle actions. Follow [Seasons](user-guide.md#seasons-objectives-sp-and-rank), [season statistics](season-statistics.md), [Habits](user-guide.md#habits), [habit statistics](habit-statistics.md), [Diary and People](user-guide.md#diary-and-people), and [Constitution](user-guide.md#constitution). The layout guide permits a deliberate larger Season hero; record any such exception.

**Manual gate:** Review active, archived, empty, and historical views. Check Habit check-ins and statistics, Diary autosave, Constitution actions, Season switching, and closeout/intermission. Confirm completion and status remain understandable without color or animation.

### Phase 6 — Money

**Implement:** Redesign Money overview, Accounts, History, Debts, Subscriptions, Organization, and Statistics. Bring page edges, module navigation, local views, forms, lists, charts, and fixed Add control into the shared system while retaining dense financial readability. Follow [Money workflows](user-guide.md#money), [Money statistics](money-statistics.md), [Money debts](money-debts.md), [Merchants and Tags](v1.1.0/phase-19-money-merchants-and-tags.md), [page rails](ui-layout-and-hierarchy.md#one-page-frame), and [chart rules](ui-design-and-motion.md#text-icons-and-data).

**Manual gate:** Inspect each Money route and currency state; add and review an expense, transfer, debt repayment, and subscription; use History filters and Organization editors. Check chart labels and exact values, destructive confirmations, long amounts/names, and fixed Add placement on mobile.

### Phase 7 — Appearance Settings and compatibility

**Implement:** Add the planned independent editable Light and Dark palettes, exact saved accent colors with derived readable companions, live previews and contrast feedback, per-role resets, one-time accent copy, and Reset all appearance. Add Normal glass as a **new** saved value while preserving `normal` and `glass`; implement the documented background behavior and honest custom-image warning. Keep System/Light/Dark preference device-local and palettes/surface style account-level. Update exports and versioned import handling with defaults for old archives. Follow [supported appearance](ui-design-and-motion.md#supported-appearance), [theme palettes](ui-design-and-motion.md#theme-palettes), [implementation boundaries](ui-design-and-motion.md#implementation-boundaries-and-known-follow-up), [Settings](user-guide.md#settings), and [account portability](v1.0.0/phase-15-account-data-portability.md).

**Manual gate:** Edit Light without changing Dark; switch System while open; copy accent and then edit its source; reset one role and all appearance; upload/remove a background; switch all three styles; reload and confirm persistence. Restore an older archive and a new archive in a safe development instance, confirming old style meanings and palette defaults. Focused compatibility regression coverage is required for the old account/archive payload shape and new export shape.

### Phase 8 — Settings, setup, onboarding, restore, and edge states

**Implement:** Finish General Settings and the first-run/setup, onboarding, restore preview, Welcome Back, and other navigation-free flows with the same typography, controls, materials, and feedback language. Keep form validation, destructive restore confirmation, timezone and rollover behavior, and installation flow intact. Follow [first setup](user-guide.md#first-setup), [Settings](user-guide.md#settings), [portable exports](user-guide.md#portable-account-exports), [first-run foundation](v0.1.0/phase-0.5-global-ui-foundation.md#first-run-setup), and [account portability](v1.0.0/phase-15-account-data-portability.md).

**Manual gate:** Walk through fresh setup and a restore preview on a development instance. Check interruption/resume, field errors, keyboard focus, mobile layout, and confirmation wording. Verify appearance remains usable before and after an account exists.

### Phase 9 — Full-app review, documentation, and internal RC

**Implement:** Audit every route and state against the [UI review matrix](ui-design-and-motion.md#review-matrix-for-every-new-or-redesigned-screen) and [layout adoption rule](ui-layout-and-hierarchy.md#adoption-rule-for-agents). Fix shared inconsistencies centrally. Update the [user guide](user-guide.md), design docs where decisions were finalized, and release notes using the repository's Added/Changed/Fixed structure. Record the final route-by-route manual checklist and any deliberate exceptions. Verify upgrades, backups/restores, old archives, new archives, and default appearance as appropriate to the final implementation.

**Release gate:** Because v2.0.0 changes persisted appearance and account archives, prepare an **internal** pre-release or release candidate first. Do not publish an internal build publicly or promote stable until the user has completed phase-by-phase manual review and the compatibility checks pass. Follow the [pre-release precedent](v1.0.0/pre-release-roadmap.md), the repository release rules, and [account portability](v1.0.0/phase-15-account-data-portability.md).

**Manual gate:** Complete a cross-module journey on desktop and mobile in the full Light/Dark × Normal/Frosted glass/Normal glass matrix. Check old-account upgrade and archive restore in a safe development instance. Review the release notes against what actually shipped.

## Completion record for each phase

Mark a phase complete only when its implementation is reviewable, its manual checklist is given to the user, compatibility implications are recorded, and the user reports the phase accepted. Then start the next phase. Keep unfinished findings visible in the phase report so the final audit can resolve them.

## Phase tracking and handoff

- This table is the quick index. The phase file is the detailed source of progress. Update both when a phase starts, is ready for user review, or is accepted: **Not started → In progress → Ready for manual review → Accepted**. Use **Blocked** only with a concrete blocker and next action. Do not call a phase Accepted based only on an agent's own visual inspection.
- In the active phase file, check a task only when its implementation is present. Check a manual-review item only after the user reports it passed; otherwise leave it unchecked and record the finding. For required compatibility coverage, record the exact result. Never infer completion from a prior phase or from an unchecked summary.
- Fill in that file's **Handoff record** before ending a work session: date, last completed task, changed files or commit, decisions, validation actually performed, user feedback, open defects, and the precise next task. Update this record even if the phase is still In progress.
- A new agent first reads this plan and the active phase file, then checks the repository status and actual code against the recorded progress. It reads the linked design and domain docs before editing. If the record conflicts with the code, correct the record and report the discrepancy. Do not mark later phases complete because a shared change incidentally affected them.
- Start the next phase only after the current phase is Accepted. If the user authorizes continuing despite an open issue, record the exception and its owner in both phase files.
